# 04 对上游交付的修改清单（同学 C 收尾）

收尾阶段发现 A、B 的交付在**整合后**存在若干会导致系统跑不起来或结果失真的问题。以下逐条记录「现象 → 原因 → 修改 → 验证」，所有修改都已进入 `src/`。

---

## A（场景 + SLAM/定位）

### A-1 车辆静止时 TF 断流，slam_toolbox 无法建图

* **现象**：`slam_toolbox` 反复打印 `Message Filter dropping message: frame 'lidar_link' … queue is full`，`/map` 长期只有个位数占据格，`/vehicle_pose` 不出。
* **原因**：`tf_bridge` 把静态外参 `base_footprint → lidar_link` 和 `odom → base_footprint` 一起**只在 `/odom` 回调里发布**。Gazebo 的 `AckermannSteering` 在车辆静止时不发 `/odom`，于是 TF 时间轴停止，扫描时刻查不到雷达变换。
* **修改**（`src/parking_slam/parking_slam/tf_bridge.py`）：
  * 静态外参改用 `StaticTransformBroadcaster` 发 `/tf_static`（对所有时间有效）；
  * `odom → base_footprint` 改为 20 Hz 定时器用当前时钟重发最近一次里程计位姿。
* **验证**：静止状态下 `/map` 正常增长，`/vehicle_pose` 20 Hz 稳定输出，`map→base` 初值为 (0,0,0)。

### A-2 航点驱动走完路径后不停车

* **现象**：巡场结束时车辆不减速，继续按最后一条速度指令行驶（差一点撞上绿化带）。
* **原因**：`demo_driver.control()` 在 `self.done` 后直接 `return`，只在结束的那一帧发过一次零速；Gazebo 的阿克曼插件会一直保持最后一条指令。
* **修改**：`done` 后**持续**发布零速，并在首次结束时向 `/driver_status` 广播 `done`（供规划层切换控制权）。
* **验证**：巡场结束后车辆稳定停住，`/driver_status` 由 `running` 变 `done`。

### A-3 `city_mapping.launch.py` 引用不存在的可执行文件

* **现象**：`ros2 launch parking_lot_city city_mapping.launch.py` 直接报 `package 'parking_slam' … libexec … does not exist`（`slam_node`）。
* **原因**：A 的实际实现是 `slam_toolbox` + `tf_bridge`，但 launch 里还留着早期自研 `slam_node` 的写法；且航点驱动直连 `/cmd_vel`，与泊车控制器抢同一个话题。
* **修改**：改为通过 `slam_toolbox` 官方 `online_async_launch.py` 启动（lifecycle 自动 configure/activate），航点驱动输出改到 `/cmd_vel_driver`，并新增 `parking_demo.rviz`。
* **验证**：一条命令即可起「Gazebo + 桥 + SLAM + 定位 + 航点巡场」。

### A-4 车辆模型转向执行器力矩偏小（调整为可复现转向标定）

* **现象**：满舵时实际前轮转角只有 0.49 rad（限位 0.61），车辆转弯半径比模型大 30%。
* **处理**：把前轮转向关节 `effort` 从 800 提高到 4000 N·m 后，实测最大等效转角**仍为 0.49 rad**，说明限制来自插件侧而非力矩。因此**保留模型改动**，同时把这条结论写进 `docs/03`，由规划层按 0.44 rad 规划、控制层加 1.4 倍增益补偿。
* **备注**：这是本次整合中对 A 模型唯一的物理参数改动，已在 `docs/03` 给出标定数据支撑。

## B（检测跟踪 + 预测 + 风险）

### B-1 模型权重路径与工作区不一致

* **现象**：`predictor_node` 默认到 `~/ros2_ws/training/checkpoints/…` 找权重，而实际工作区是 `~/apa_ws`，节点启动即告警「未找到模型权重，节点将不输出预测」。
* **修改**：launch 中以参数 `model_path` 显式指向 `~/apa_ws/training/checkpoints/trajectory_transformer.pt`；同时在仓库里补齐 `training/`（训练脚本，与 `src/` 同级）+ 文档说明需先训练。
* **验证**：CPU 40 epoch 训练完成，`val_ADE = 0.319 m`（验收阈值 0.4 m），预测节点正常加载并输出。

### B-2 风险节点兜底车位坐标有误

* **现象**：`risk_node` 的兜底 `target_spot_x/y = (17.0, -9.75)` 是**世界坐标**下的一个**已被占用**车位；而 `/target_spot` 约定在 map 帧。
* **影响**：C 未发布 `/target_spot` 之前（或话题丢失时），B 的泊车走廊指向错误位置，风险等级失真。
* **修改**：launch 把兜底值改为 map 帧的 W5 车位中心 `(8.75, -7.5)`，并在文档中注明「正常运行时应由 C 的 `/target_spot` 覆盖」。
* **验证**：C 发布 `/target_spot` 后风险等级随目标车位正确变化。

### B-3 启动顺序与话题依赖

* **现象**：三个节点与 C 的节点同时启动时，偶发某个进程卡在 `rcl_node_init`（WSL2 + Fast-DDS 的 participant 竞争）。
* **处理**：`parking_demo.launch.py` 把 6 个节点错开 2–3 s 启动，并统一使用 UDP-only 的 Fast-DDS 配置（`config/fastdds_udp_only.xml`）。

## 未修复但已知的问题（如实记录）

1. **B 的 `detection_node` 在极近距离（< 1 m）会漏检**：激光在车体边缘有遮挡，属 B 模块的已知限制，不影响本层的泊车决策（C 只用 `/risk_level`，且危险时会停车等待）。
2. **B 的模型 ADE 0.319 m 与文档里的 0.198 m 有差距**：本次在 CPU 上重训（40 epoch）得到的权重略差，属训练预算差异，仍满足 < 0.4 m 的验收线。
3. **平行车位未纳入自动选位**：见 `README.md` 第 5 节「已知限制」。
